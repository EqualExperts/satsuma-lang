# Feature 39 — Correctness by Default

> **Status: PROPOSED** (2026-08-03) — raised after reading the toolchain looking
> for the mechanism behind its recent defect clusters. The finding: the defects
> have been *specification* defects, not implementation defects. In each case the
> code faithfully implemented a rule that was wrong, under-specified, or in
> tension with a sibling rule, and a green suite said so. This feature is the set
> of mechanical changes that move those rules from prose into the build.
>
> **State this PRD was written against:** `main` at `4d17c505`. Every count and
> file reference below was measured against that commit.
>
> **What this feature is not.** No language change and no rewrite in another
> language is proposed. No verified-implementation work (extraction from Dafny,
> F\*, or Lean) is proposed — that targets implementation correctness, which is
> not what has been failing. Every requirement below is ordinary TypeScript, one
> code generator, and one optional modelling spike.
>
> **Relationship to Feature 38.** Complementary, and partly contentious in
> scheduling. Feature 38 is *deciding* what the hierarchical coverage rules
> should be; this feature is making whichever rules it settles on
> machine-checked. R4 wants to land while 38 is still inside
> `coverage-paths.ts`; R2, R3 and R7 want 38 finished first, since they would
> otherwise model rules that are still moving. See Open Question 5.

## Goal

Make the invariants this toolchain already documents enforceable by the build
rather than by review, so that a rule, once decided, cannot quietly stop holding.

1. **A grammar change cannot silently change behaviour.** A renamed or removed
   node kind breaks compilation instead of leaving a branch that stops matching.
2. **Path and ref identity is a type distinction, not a convention.** The three
   flavours of field path and three spellings of a schema ref stop sharing one
   type.
3. **The coverage rules are checked on inputs nobody chose.** The ADR-034–041
   rule set gains generated-input properties alongside its example tests.
4. **The strongest checks the repo already owns apply everywhere**, not to one
   package in nine.

## Background — measured state

### The defect pattern

Four recent clusters, one shape:

| Defect | What the code did | Why tests passed |
|---|---|---|
| `sl-joeq` | Resolved coverage by field *name* where the rule needed *path* | It implemented the documented rule; the rule was wrong |
| `sl-qead` | Let a spread redeclare a field the body declared | No rule existed. **ADR-041 had to amend ADR-035** to state one |
| ADR-038 | — | Written to *constrain* ADR-037 after a counterexample surfaced |
| `sl-iqud`, `sl-qxyl` | Matched one spelling of a schema ref out of three | All three spellings have the type `string` |

Verifying the implementation against the specification would have caught none of
these. What catches them is a stated invariant plus an input the author did not
choose, or a type that makes the confusion unrepresentable.

### The CST is addressed by unchecked strings

`SyntaxNode.type` is `string` (`satsuma-core/src/types.ts:11`) and
`child(node, type)` takes `string` (`satsuma-core/src/cst-utils.ts:25`).
Measured at `4d17c505`:

| Package | `node.type === "…"` sites | Distinct kinds | `child`/`children(n, "kind")` sites |
|---|---|---|---|
| `satsuma-core` | 181 | 51 | 55 |
| `satsuma-cli` | 221 | 44 | 2 |
| `satsuma-lsp` | 73 | 32 | 49 |
| `satsuma-viz-backend` | 59 | 32 | 68 |

534 comparisons and 174 kind-keyed lookups, none of them checked against the
grammar. There are also 12 `switch (node.type)` sites across core, LSP and
viz-backend whose arms are unchecked string literals.

The grammar declares **60 named node kinds** (plus 39 anonymous tokens) in
`tooling/tree-sitter-satsuma/src/node-types.json`. That file is tracked, is
regenerated by `tree-sitter generate` on every grammar build, and **is consumed
by nothing** — no script, test, or build step reads it.

Two facts from cross-referencing it against the code:

- **53 of the 60 named kinds** are compared somewhere. The other seven —
  `boolean_literal`, `dotted_name`, `field_path`, `map_key`, `map_value`,
  `qualified_dotted_name`, `source_file` — never are. Some are legitimately
  reached another way (`source_file` is `tree.rootNode`); whether all seven are
  is exactly the question nobody can currently answer cheaply.
- **Four anonymous tokens** are compared as if they were kinds — `record`,
  `list_of`, `enum`, `slice`. These are correct today, and they mean a generated
  type must cover anonymous tokens too or it will reject working code.

This is the mechanism ADR-031 was written about, one layer up: ADR-031 made
mis-*parses* loud, and mis-*matches* are still silent.

### The domain is modelled as `string`

`schemaLocalFieldPath` (`coverage-paths.ts:221`) takes `fieldRef: string`,
`schemaRefs: readonly string[]`, `otherSchemaRefs: readonly string[]` and
returns `string | null`. Its own doc-comment explains that three spellings of one
schema circulate (`crm::customers`, `customers`, `::customers`) and that field
refs arrive in authored, container-qualified, and schema-local forms. All six are
`string`. `buildCoveredFieldPaths` accepts any `Iterable<string>`, which is what
made `sl-joeq`'s bare-segment registration type-correct.

There are **no branded or nominal types anywhere in the repo** (no `__brand`, no
`unique symbol` in any `src/`), and **no `assertNever`** or equivalent
exhaustiveness helper.

ADR-039 — consumer models keep the authored form, core resolves at the point of
use — is a type distinction currently enforced only by prose.

### What is already good, and is not re-done here

This feature deliberately does not duplicate work already in place:

- **Formatter round-trip properties exist and run over the whole corpus.**
  `satsuma-core/test/format.test.js:67-90` asserts, for every file under
  `examples/`, both `format(format(x)) === format(x)` and parse-tree structural
  equivalence between `parse(x)` and `parse(format(x))` via a `structureOf`
  comparison; `:849` adds error-free reparse of formatted output; and
  `satsuma-cli/test/diff.test.ts:677` covers `fmt`-round-trip structural
  identity (`sl-dxjh`, ADR-033). The gap is the *inputs*, not the properties.
- **`strict` and `noUncheckedIndexedAccess`** are on in six of the seven
  TypeScript packages. Only `satsuma-viz/tsconfig.json` omits
  `noUncheckedIndexedAccess`.
- **The ADR rules are cited by tests**, unevenly: ADR-036 at 13 sites, ADR-022
  at 11, ADR-038 at 6, ADR-037 at 5, ADR-034 at 5, ADR-040 at 2, ADR-035 at 2 —
  and **ADR-039 and ADR-041 at none**.
- **`MetaEntry`** (`types.ts:94`) is a correct discriminated union and is the
  model R6 asks `FieldDecl` to follow.

### The gaps

- **No property-based testing anywhere.** No `fast-check` or equivalent in any
  package. Every check above — including the corpus round-trips — runs on inputs
  a human chose, which is the class of input that has repeatedly failed to
  contain the counterexample.
- **Type-aware ESLint runs on one package.** `tseslint.configs.recommendedTypeChecked`
  is applied to `tooling/satsuma-cli/src/**/*.ts` only (`eslint.config.mjs`).
  `satsuma-core` — the most invariant-dense package in the repo — gets no
  type-aware linting at all, and `satsuma-lsp`, `satsuma-viz-backend` and
  `satsuma-viz` are not linted as TypeScript beyond the JS baseline.
- **No exhaustiveness enforcement.** 138 `case "…":` labels across the packages,
  no `switch-exhaustiveness-check`, no `assertNever`.
- **`FieldDecl`** (`types.ts:98`) is a bag of eight optional fields in which
  `type: "record"` implies `children`, `isList` implies an element type, and
  `hasSpreads` implies `spreads` — none of it expressible to the compiler.
- **A configured check that nothing runs.** `satsuma-cli` defines
  `test:typecheck` (`tsc --project tsconfig.test.json`), and it is wired into
  neither `.github/workflows/` nor `scripts/run-repo-checks.sh`. It currently
  fails: `test/canonical-ref.test.ts` builds `FileData` literals missing
  `imports`, `nlRefData` and `notes`. Test files are excluded from the linted
  and typechecked surface by design (`eslint.config.mjs` notes the
  `import.meta.dirname` module-target conflict), so ~31k lines of test code
  sit outside both.

## Problems

### P1 — A grammar rename is a silent behaviour change

534 unchecked comparisons mean a renamed kind produces a branch that never
matches, a silently empty extraction, and a green suite unless a test happened
to cover that construct. Four defects of the neighbouring class (a construct the
walker did not handle) were found by inspection during Feature 38 and none by a
test.

### P2 — Path and ref identity is a convention, not a type

Passing an authored path where a schema-local one is required, or a bare leaf
name where a qualified path is required, is a type-correct program. That is the
literal shape of `sl-joeq`, and nothing prevents its recurrence.

### P3 — The rules are tested only on inputs we thought of

The coverage rules are algebraic — prefix-closed path sets over finite field
trees — and every one of the recent failures was a small counterexample
(same-named siblings at different depths; a spread that redeclares; a
whole-record arrow over a nested subtree). Example-based tests find these only
after someone has thought of them.

### P4 — Most packages sit outside the strongest checks we already own

The checks that would surface a stale kind comparison (`no-unnecessary-condition`)
or a missing switch arm (`switch-exhaustiveness-check`) are configured for one
package, and it is not the one holding the invariants.

### P5 — Rules whose mutual consistency has already failed are checked one example at a time

ADR-041 amends ADR-035; ADR-038 constrains ADR-037. Each amendment was prompted
by a counterexample found in production use, and nothing checks the current rule
set for the next one.

## Requirements

### R1 — Generate node-kind types from `node-types.json` (fixes P1)

- A generator in `tooling/tree-sitter-satsuma/` emits a TypeScript module from
  `src/node-types.json`: a `SatsumaNamedKind` union of the 60 named kinds, a
  `SatsumaAnonymousToken` union of the 39 anonymous ones, and
  `SatsumaNodeKind = SatsumaNamedKind | SatsumaAnonymousToken`.
- It runs in the grammar package's `build` alongside `tree-sitter generate`, and
  the output is tracked like the other generated artifacts. CI fails when the
  committed output is stale — the same discipline `parser.c` already has.
- `SyntaxNode.type` becomes `SatsumaNodeKind`; `child()` and `children()` take
  `SatsumaNodeKind`. Both live in `satsuma-core`, so all four consumer packages
  inherit the narrowing with no call-site changes except genuine mistakes.
- The four anonymous-token comparisons (`record`, `list_of`, `enum`, `slice`)
  must keep compiling — they are correct.
- Ordering note: land this before R6 enables `no-unnecessary-condition`, which
  is what turns a now-impossible comparison into a reported error rather than a
  silently dead branch.

### R2 — Property tests for the coverage algebra (fixes P3)

Add `fast-check` as a `satsuma-core` dev dependency and generate field trees,
arrow sets and spread combinations. The properties are already written down as
ADRs and module docs; state them as code:

| Property | Source |
|---|---|
| `pct === 100 ⟺ every leaf covered`, `pct === 0 ⟺ no leaf covered` | ADR-040 |
| No path appears twice in a coverage result | ADR-041 (0 test citations today) |
| A directly-covered container covers its whole subtree | ADR-037 |
| Target-side whole-structure expansion requires a container source | ADR-038 |
| `ancestors` contains exactly the proper prefixes of `direct`, and nothing else | `coverage-paths.ts:60`, unasserted prose |
| `schemaLocalFieldPath` is idempotent — applying it twice equals applying it once | derived from `coverage-paths.ts:221` |
| A schema's percentage is unchanged by re-nesting: same leaves, same arrows, same number | Feature 38 R3 |
| Coverage never *decreases* when an arrow is added | new — the monotonicity `--fail-under` implicitly assumes |

Extend the existing corpus round-trips (`format.test.js:67-90`) with generated
sources for the same two properties, rather than replacing them.

### R3 — A naive reference model, differentially tested (fixes P3)

Implement coverage a second time in ~100 deliberately slow, obviously-correct
lines — materialise every declared path, brute-force membership, no
optimisation — and assert the real implementation agrees over R2's generated
workspaces.

`sl-joeq`'s bare-segment registration cannot survive this: nobody writes it into
a naive model by accident. The model doubles as executable documentation of the
semantics, and is the artifact R7 would formalise if that spike goes ahead.

Deliverable is a test-only module. It must not become a second production
walker — the mistake `sl-vu22` is removing.

### R4 — Brand the path and ref types (fixes P2)

- Introduce branded types in `satsuma-core` with smart constructors as the only
  way to obtain one: minimally `AuthoredFieldRef`, `SchemaLocalPath`, and for
  refs `AuthoredEntityRef` vs `CanonicalEntityRef` (the distinction
  `canonical-ref.ts` already draws in prose, and that ADR-039 relies on).
- `schemaLocalFieldPath` returns `SchemaLocalPath | null`;
  `buildCoveredFieldPaths` and `buildCoveredFieldSet` accept only
  `Iterable<SchemaLocalPath>`; `isCoveredFieldPath` and `isCoveredPath` take
  `SchemaLocalPath`.
- Brands are erased at runtime — no serialization, `--json` output, or protocol
  shape changes. `@satsuma/viz-model` types stay plain strings at the boundary,
  with re-branding at the consumer's entry point.
- Scope discipline: brand the *coverage and ref* domain only. Branding every
  string in core is out of scope (Open Question 2).

### R5 — Grammar-kind census test (fixes P1)

A test asserting that every named kind in `node-types.json` is either referenced
by an extractor or listed in an explicit, commented ignore set. The seven
currently-unreferenced kinds seed that set, each with a one-line reason. A new
grammar rule then fails the suite until someone decides what it means. Depends
on R1.

### R6 — Uniform static checking (fixes P4)

- Extend `recommendedTypeChecked` to `satsuma-core`, `satsuma-lsp`,
  `satsuma-viz-backend` and `satsuma-viz`, and enable
  `@typescript-eslint/no-unnecessary-condition`,
  `switch-exhaustiveness-check`, and the `no-unsafe-*` family. Expect a
  one-time cleanup; land it per package.
- Add `noUncheckedIndexedAccess` to `satsuma-viz/tsconfig.json`, the only
  package missing it.
- Fix the `FileData` literals in `satsuma-cli/test/canonical-ref.test.ts` and
  wire `test:typecheck` into `scripts/run-repo-checks.sh` so the check the
  package already defines actually gates commits. Then decide the general
  question it exposes — whether the test surface stays outside type-aware
  checking (Open Question 7).
- Convert `FieldDecl` to a discriminated union on the leaf/record/list axis,
  modelled on `MetaEntry` in the same file, and add an `assertNever` helper to
  core. `FieldDecl` is on core's public surface, so this is a breaking change to
  a shared type and needs its consumers migrated in the same ticket.

### R7 — Model the coverage rule set for consistency (fixes P5) — spike

Encode the ADR-034–041 rules relationally — Alloy, or Z3 through the Python
tooling the repo already lints (`ruff.toml`, `requirements-dev.txt`) — and ask
for a small counterexample where they conflict. The deliverable is a report plus
the model, not production code: either "no counterexample within scope N", which
is a real result, or the next ADR amendment found before a user finds it.

Time-boxed. Gated on Feature 38 closing, since it is still changing these rules.

### R8 — A denotational section for the spec (fixes P5 at the root) — spike

`docs/developer/SATSUMA-V2-SPEC.md` is 1,572 lines and entirely syntactic:
lexical rules, block structure, vocabulary, four worked examples. It never says
what a mapping *means*. That is why coverage questions get settled by ADR fiat,
one counterexample at a time, and why ADRs end up amending each other.

Draft a short section: a mapping denotes a partial function from source records
to target records; an arrow denotes an assignment to a target path; coverage is
the set of target leaf paths in its image. Then re-derive ADR-037, ADR-038 and
ADR-041 from it and check they follow. If one does not, that is the finding.

Prose first. Mechanisation is not in scope for this feature.

## Acceptance Tests

Cases 1–12 must **fail** against `4d17c505`.

### Generated kinds (R1, R5)

1. `node.type === "schema_blok"` (typo) fails `tsc` in `satsuma-core`.
2. `child(node, "mapping_bdy")` fails `tsc`.
3. `node.type === "record"` (an anonymous token) still compiles.
4. Renaming a rule in `grammar.js` and regenerating makes at least one existing
   comparison fail to compile.
5. Committing a stale generated kinds module fails CI.
6. Adding a named rule to the grammar fails the R5 census test until it is
   handled or explicitly ignored.

### Branded types (R4)

7. `buildCoveredFieldPaths(["city"])` — a bare leaf name, the literal `sl-joeq`
   defect — fails `tsc`.
8. Passing an authored ref where `SchemaLocalPath` is required fails `tsc`.
9. `--json` output is byte-identical to `4d17c505` for every file under
   `examples/` (brands are erasure-only).

### Properties (R2, R3)

10. Each property in R2's table has a generated-input test, and each names its
    ADR in a purpose comment.
11. Reverting `sl-joeq`'s fix (restoring bare-segment registration) makes the
    R3 differential test fail — the property suite catches the historical
    defect, not just today's code.
12. Reverting `sl-qead`'s fix makes the ADR-041 uniqueness property fail.

### Static checking (R6)

13. A non-exhaustive `switch` over a `FieldDecl` variant in core is an ESLint
    error.
14. A comparison against a kind the grammar no longer has is reported by
    `no-unnecessary-condition` rather than passing as dead code.

### Regression

15. Every existing suite passes: core, cli, lsp, viz, viz-backend, vscode, the
    315 grammar corpus parses, and the pytest-bdd smoke suite.
16. No change to `satsuma coverage --json`, VizModel, or LSP protocol output on
    any example.

## Out of Scope

- **Coverage semantics.** What the rules *should be* is Feature 38. This feature
  checks whichever rules 38 settles on.
- **New lint rules for users.** `type-mismatch-direct-arrow` and
  `lineage-cycle` are Feature 37. R6 is about linting *our* source.
- **A rewrite in another language**, and **verified-implementation extraction**
  (Dafny, F\*, Lean → JS). Both target implementation correctness, which is not
  the failing layer, at a cost far above the rest of this feature.
- **Mechanised proof of the spec.** R8 delivers prose; R7 delivers a
  counterexample search. Neither is a proof obligation on the implementation.
- **Fuzzing the parser and external scanner.** Generating from `grammar.json` to
  hunt for crashes, hangs, and scanner mis-tokenisation is a credible companion
  item, but it targets the parser rather than the analysis layer and deserves
  its own scoping.
- **Performance.** No requirement here is motivated by speed.

## Open Questions

1. **Where does the generated kinds module live?** Emitting from
   `tooling/tree-sitter-satsuma/` keeps it next to `node-types.json` and the
   other generated artifacts, but that package currently exports no TypeScript
   and every consumer would gain a dependency on it. The alternative is a core
   build step that reads the grammar package's JSON. Proposed: emit in the
   grammar package, re-export from `satsuma-core` so consumers keep one import.
2. **How far do brands go?** R4 scopes them to coverage paths and entity refs.
   Candidates deliberately left out: file URIs (already normalised by
   `source-files.ts`), NL `@ref` text, and namespace ids. Proposed: coverage and
   refs only, and revisit once the ergonomics are known.
3. **Does `fast-check` belong in `satsuma-core`'s dev dependencies?** It is
   dev-only so it does not reach the CLI tarball's `bundleDependencies`, but it
   does enter `npm audit` scope for a package that currently has one runtime
   dependency. Proposed: accept it; the alternative is hand-rolled generators.
4. **Is `FieldDecl`'s union worth its migration?** It is on core's public
   surface and used by the CLI, LSP, viz-backend and viz. The eight-optional bag
   is a real modelling defect, but this is the one requirement here with a
   consumer-visible blast radius. Proposed: keep it in R6 but ticket it
   separately, and schedule it after Feature 38 stops changing coverage types.
5. **Sequencing against Feature 38 — the real contention.** R4 touches
   `coverage-paths.ts` and `coverage.ts`, which `sl-0pun` and `sl-r6b0` are
   still changing; R2, R3 and R7 would model rules that are still moving.
   Proposed: R1, R5 and R6 start immediately (they touch neither), R2 and R4
   wait for `sl-fmx0`'s descendants to land, and R7/R8 wait for the epic to
   close. Alternative worth considering: land R2's properties *during* 38 as the
   acceptance harness for its remaining tickets, accepting churn in exchange for
   catching 38's own regressions.
6. **Should the R3 reference model be exported?** Test-only keeps it honest.
   Exporting it from core would let the LSP and viz test suites use it as an
   oracle too, at the risk of it drifting into a second walker.
7. **Does type-aware checking extend to the test surface?** Roughly 31k lines of
   test code are outside it today, and `eslint.config.mjs` records a concrete
   blocker: tests use `import.meta.dirname`, which needs a higher module target
   than the `node16` the packages compile against. Proposed: fix the one broken
   typecheck and gate it in CI (R6), and treat raising the test-file module
   target as separate work rather than smuggling a toolchain bump into this
   feature.
