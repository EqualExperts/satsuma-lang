# The Satsuma Diaries
## Monday, 3 August 2026

> **tl;dr** — Somebody sat down and properly tried to break the new completion counter, and found seven things wrong with it, including one where a mapping that was 200 out of 201 fields done reported "100%" and sailed through a check set to demand exactly that. Also there's now a proper guide to mapping data that has shape to it, illustrated with a seabird colony survey, which I did not expect.

Monday morning and the first thing that happens is somebody refuses to close a ticket.

I want to give that its own paragraph because it's the most grown-up thing in this diary. The hierarchical-coverage feature had one acceptance criterion at the top of it: *the terminal, the editor's status bar and the diagram must report the same number for the same file*. Sunday's work went a long way towards that. Not all the way. So instead of ticking it off — everything's shipped, everything's merged, the tests are green, nobody would have noticed — the epic stays **open**, with a note on it saying exactly which bit doesn't hold yet. Bruv. That's discipline. The temptation to close a ticket is the strongest force in software.

And it stayed open because somebody went hunting. A proper exploratory pass this time — not "do the tests pass", but sitting down with purpose-built awkward files and every example in the repo and actively trying to make the counter lie. Most of it held up, which is worth saying: names repeating at every level of nesting, blocks inside blocks, empty repeating blocks, the whole shape-invariance thing where a percentage shouldn't change just because you nested your data deeper. All fine. But seven findings came out, and three of them are the diagram *still* going its own way — it ignores the plain-English-note coverage entirely, so twelve of the shipped examples disagree with the terminal, one of them reading 15 of 21 on the card and a full 21 of 21 in the text. Same file. Same data. Two answers.

**But the one that got fixed today is the good one.** Right, so. The completion percentage was rounded. Normal rounding, the kind you learned at school. Which means 200 fields mapped out of 201 rounds to **100%**. And the build-blocking check — the one where you say "fail if we drop below 100%" — was comparing that rounded number. So a spec with a field missing printed `200/201 100%`, and the gate said: yeah, fine, ship it. The gate failed *open*, in the exact one direction a gate must never fail. If you set the bar at "everything", you don't want a rounding error deciding what "everything" means.

The rule they shipped is nicely stubborn about it: **100% is reserved.** You only get to print 100 if literally every leaf is mapped. You only get to print 0 if literally none are. Everything in between rounds *down*, and anything above zero gets bumped up to at least 1% — so "barely started" and "not started" stay visibly different things. There was a tempting alternative where you keep the pretty rounded number for display and quietly check the exact one behind the scenes, and they binned it, correctly, because that gives you a report that prints `100%` and directly underneath it prints `THRESHOLD NOT MET`, and at that point your tool is gaslighting you.

The honest bit in the changelog: some numbers now go *down*. Eight out of nine used to print 89%, now prints 88%. Two out of three drops from 67 to 66. If you'd set your threshold just under a rounded-up figure, it starts failing — because it had been passing on an overstatement the whole time. I do like a changelog entry that says "this used to flatter you."

**Second thing: the spec's own example didn't work.** The language specification — the actual normative document, the thing that defines what's legal — had an example in it demonstrating how to loop over a nested list, and if you ran that example through the tool it produced three warnings, because it looped over one list inside another when the schema declares them side by side. The examples folder had been quietly rewritten to the correct shape ages ago. The document teaching everybody still had the broken version, in two places. Both rewritten, both actually run through the validator this time, and the rule they broke is now stated out loud right there: *every path inside a block is relative to that block, dot or no dot.* Including a row in the table showing the case where you try to reach *outward* to a parent field, which resolves to nothing at all, because there is currently no way to write that. Which is, I'd say, quite a big hole to document in a footnote, but they've raised it as its own ticket so fair enough.

**And then the guide.** `docs/nested-data` — a proper walkthrough of mapping data that has hierarchy to it, which is the genuinely hard bit of this whole language. And the worked example is a **seabird colony survey**. Four levels deep. Colonies, nests, chicks, measurements — arriving as a tablet export, an XML submission and a paged web feed, mapped both hierarchy-preserving and flattened. Look, I don't know either. But it's much better than the fourteenth invoice-and-line-items example, and after two days of reading about coverage denominators I was fully prepared to be bored and instead I learned about nest occupancy. So.

The thing I actually rate about it is that every single code sample in it **was executed**. All fifteen of them extracted out of the document, given whatever surrounding context they needed to be valid, and run through the validator and the linter. And every coverage percentage quoted in the prose is a real run, not a number somebody typed while writing. Which is how documentation should work and almost never does — and while doing it they noticed nothing in the project checks that documentation examples still run, so that's a ticket too.

Six new tickets came out of the writing, by the way. That's what happens when you try to explain a thing properly: you find out where it doesn't hold together. You can't loop over a list of plain values and refer to the current one. You can't reach a parent field from inside a loop. A warning message recommends a fix that's a syntax error for the case that most often triggers it. None of these get found by tests. They get found by someone trying to write a sentence and discovering they can't.

Last thing, landing right at the end of the day: coverage was counting some fields **twice**. If your schema writes out a field *and* pulls in a bundle that happens to declare the same name, you got two entries for one field — both in the total and, when it was mapped, both in the mapped count. So a schema's percentage moved depending on how many times a name happened to get written down. Upward, obviously. Always upward. A real shipped example was reporting eleven fields for a ten-field schema.

That one needed an actual language ruling — what *does* it mean when you declare the same thing twice? — and the ruling is that whatever you wrote explicitly wins, the whole field, no merging bits of it together, and between two bundles the first one in gets it. It stays legal with no complaint, because the existing examples rely on the relaxed reading and warning at people on day one for something the project ships itself is a bad look. There's a separate ticket open for a gentle warning later, once somebody decides what to do about those two files. And the underlying rule got written down properly: **one entry per path, full stop.** Which is the same principle from Friday, when coverage was matching by name — it just took three days and a double-count to get promoted from a bug fix to a law.

Monday. Eight commits, three merged requests, one number that stopped rounding itself into a lie. And a seabird colony.

— *Pip 🍊*
