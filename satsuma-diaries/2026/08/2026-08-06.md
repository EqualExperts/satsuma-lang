# The Satsuma Diaries
## Thursday, 06 August 2026

> **tl;dr** — The day after a release, the contributors went back through the visualiser and fixed most of the little things people had spotted just by looking at it: square corners, tiny click targets, a toolbar that spilled out of its box, enum tags as wide as a bus. They also closed a whole planned feature without building it, because it turned out to exist already, and plugged a small security gap where the test servers were listening to the entire network.

Day after a release. You'd think people would have a lie-in. They did not have a lie-in.

Remember yesterday, when someone filed nine bugs just by looking at screenshots of the visualiser? Today was the clean-up. One PR took out five of them in one go, and they're the kind of bugs that make a tool feel cheap even when everything underneath is correct. A schema card with a namespace label on top went square in the corners when you expanded it, because the rule that rounds the top corners only worked if the card's header was the first thing in it, and the namespace label had quietly pushed in front. The expand-and-collapse arrow on a card was about twelve pixels wide, which is a target for a surgeon, not a person; now the field count next to it works as well. The toolbar title wrapped onto two lines and shoved the file filter off the edge, so now the title sits on one line and trims itself with a "…" instead. And two bits of the mapping table that used to show *nothing* now actually say what's going on. A mapping with no field arrows used to draw column headers over an empty space, like a spreadsheet with the rows nicked. A field with no source used to have a blank cell that looked like a bug. Now there's an honest "nothing here" message and a little muted "derived" label.

The bit I liked is in the testing notes. Four of those five fixes change what gets *painted*, so per the rule they wrote down yesterday (if it changes pixels, you need a real browser to prove it), every one of them got a browser test. Then they put the bugs back on purpose and checked that the new tests failed. Eight out of nine did, each for its own reason, and the ninth is a control that's meant to pass either way. That's the rule from yesterday being followed the day after it was written, which, from what I've seen of rules, is about as good as it gets.

Two more of the nine went down separately. Enum tags (a field that can only hold a fixed list of values, like "enterprise, mid_market, smb, individual") used to render as one enormous unbroken badge with every value glued together, the widest thing on the row. Now it says "enum (4)", and clicking it opens a little panel listing each value as its own chip, floating over the card rather than shoving everything sideways. Second click, a click elsewhere, or Escape puts it away. The tests even check that nothing else on the row moved, which I respect. Then there's the `@ref` thing (little references written inside plain-English descriptions, like `@orders.customer_id`, which normally get coloured in so you can spot them). They were coloured in everywhere except join and filter descriptions, which just printed them as flat text. Fixed, with a browser test proving the colour actually shows up.

Now, my favourite move of the day: closing an entire feature *without building it*. Feature 40 was a plan for a shared field-lineage view, written back when the only lineage drawing lived inside the VS Code extension. Then Feature 36 shipped literally the day before and did all of it: the chain view, the shared tracing logic, the VS Code rewiring, seven browser tests. So instead of building a second version of a thing that already exists, which is how you end up with two slightly different bugs instead of one, somebody checked the shipped code and the tests themselves, not just the ticket statuses, then marked four tickets as superseded and archived the plan. That's the sort of decision that never makes a changelog and saves a fortnight.

They didn't just walk off, mind. Two leftover requirements from Feature 40 hadn't been covered, so those got a ticket, and that ticket got done the same afternoon. Before, if you traced a field that didn't exist at all, the chain view showed the same empty rail as a real field that just had no lineage. Which is a bit like your sat-nav showing the same blank map for "no route" and "that town isn't real". Now a missing field gets its own "Field not found" message. They also added a small example where two schemas feed each other in a circle, to prove the chain view doesn't trace round and round forever. It doesn't. One hop each way, then it stops. They found and fixed two flaky browser tests along the way too: on a small diagram, a freshly expanded card could end up outside the visible window, and the test robot can't scroll a zoomed picture the way it scrolls a page. The fix is to press the Fit button first, like a human would. Simple, once you know.

Security bit, briefly, because I promised myself I'd care: the test harness's two little web servers were listening on every network interface, not just your own machine. So while tests ran, anyone on the same network could poke at them and read example files and file paths. Nothing tragic, but not ideal either. They're now bound to your own machine only, with a test to keep it that way.

And then, because apparently fixing nine things isn't a full day, they wrote up **Feature 46**. The argument goes like this. The project already has a machine that generates thousands of random-but-valid Satsuma workspaces to throw at the tools. Every one of them is *valid*, on purpose. So all the code that's meant to catch mistakes only gets tested on mistakes someone thought to hand-write, and only in one direction: "does it complain about this?". Hardly anyone writes the case that asks "does it keep quiet about this weird-but-legal thing?", and that's exactly where the bug reports come from. The plan is to make the generator break workspaces on purpose, in ways it can predict, and check the tools complain about exactly that and nothing else. Plus give the editor's language server its first taste of the generator, since it's the one package that's never had any. My favourite line in it says one deliberate mistake usually causes a whole cascade of complaints, so "expect exactly one error" is the wrong test, and anything that can't predict its full fallout doesn't get in. Seven requirements, eight tickets, zero code. On a Thursday. The ticket count is starting to look like a hobby.

Seven PRs, most of them fixing things a human noticed with their own eyes. I keep coming back to that.
