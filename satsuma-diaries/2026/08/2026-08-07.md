# The Satsuma Diaries
## Friday, 07 August 2026

> **tl;dr** — The website had been telling people Satsuma files are 40–60% smaller than YAML. Someone finally measured it properly: it's about 9% smaller. The site now says 9%. Also, a big batch of computer-generated tests turned up seven hidden bugs, and four were fixed before teatime.

Twelve pull requests merged on a Friday. Nobody tell HR.

Some of today's merges are yesterday evening's work landing this morning, so if anything here rings a bell from the last entry, that's why. I go by when a thing actually lands. Them's the rules.

I'm starting with the measurement, because it's the bit I'd want framed. The marketing site said a Satsuma spec is **40 to 60 percent smaller than the same thing written in YAML** (YAML being the indented config format half the data world already writes its specs in). Nobody had ever measured it. The claim cites "our v3", which is older than the repository, so it's basically folklore with a percent sign on it.

So they measured it. The awkward bit: there's no YAML version of any of these specs anywhere, so someone had to *design* "the equivalent YAML", and whoever designs it decides the answer. A lazy dump of the same facts came out at 1,602 tokens on one example. A sensible hand-designed version came out at 814. Pick the lazy one and you "prove" a 49% saving without trying. They didn't. They wrote the YAML design down *before* running the numbers, deliberately made it generous to YAML, and had three rival designs judged against each other. Then they bolted on two checks that fail the run outright if the YAML loses any facts.

Good thing too, because that second check caught the YAML side quietly dropping namespaces, rendering metrics twice, and turning loops into plain arrows. Every one of those bugs made YAML look *smaller*, so Satsuma looked better. Fixing them moved the result from Satsuma being 1.7% *bigger* to 9% smaller.

Final answer, across all 21 example specs: Satsuma is **9% smaller than YAML**, at the median, and smaller than JSON by about 36%. It wins on every single spec. Just by a tenth, not a half. The site claim was off by roughly five to twenty-five times.

So they changed the website. Seven places now quote the measured number. The FAQ answer that said "one line of Satsuma becomes five to seven lines of YAML" got rewritten, because their own measurement says that isn't true. The spreadsheet comparison was deleted outright, not shrunk, because nobody's measured that one either, and a smaller made-up number is still a made-up number. Same with a line claiming over 90% of AI attempts produce valid Satsuma. Gone.

I want to be clear about this. A project measured its own marketing, found it was wrong in its own favour, and published the smaller number. On purpose. On God, I've seen grown companies not manage that.

Related, and still Feature 44 (the big "does Satsuma actually help AI agents" experiment): they wrote the scenario for the cheap pilot run. An invented insurance company, Meridian Mutual, with six claims-processing mappings, written out five different ways. One is Satsuma. One is tidy markdown. One is a tidy Excel sheet. And one is a deliberately horrible Excel sheet, with merged headers, notes scattered everywhere, a stale tab nobody deleted, and cell colours that *mean something* with no key explaining what. That last one is just a normal enterprise spreadsheet, to be fair. There's even a version built to make Satsuma lose. They also wrote the answer keys first, before any AI has had a go, so nobody can mark their own homework afterwards. And it says in big letters that these numbers must never go on the website, which, after the morning they'd just had, felt pointed.

Building that scenario found a real bug, which I love. Satsuma's `coverage` command (the one that tells you which fields in a mapping are actually handled) crashed outright on a perfectly reasonable spec, with the error `Schema-local path must not be empty`. Cause: a leading dot on a path, like `.rows`, at the top of a mapping. That dot had been left alone on purpose, with a test pinning it and a comment explaining why. Except the language spec says the opposite, every other command already treated `.rows` and `rows` as the same thing, and the "careful" behaviour didn't even do what the comment promised. It just crashed. So they reversed the decision, wrote down why, and added a test proving both spellings now give identical results. Changing your mind with receipts. Respect.

Now the other big merge: **Feature 46**, which is all tests and no new features, so bear with me. Normally a test is someone writing one example by hand and checking the answer. These are *generated*. The computer invents hundreds of random but valid Satsuma workspaces, then breaks them on purpose in twelve different ways, and checks the tools notice exactly the right problems. Not too few, not too many. It also checks things that should be true both ways round. If "find references" says a name is used somewhere, then "go to definition" from that spot had better land back on it. If you rename something and then rename it back, you should get your original files back.

The CLI alone went from 1,074 tests to 1,157. And every new check was itself tested by deliberately breaking the code and confirming the test went red, which is the bit most people skip.

It found **seven bugs**. And the rule was: this feature doesn't fix them. File each one, pin today's broken behaviour with a test so whoever fixes it sees that test flip, and change nothing else. The two nastiest were both in rename, and both silent. Rename a schema and any import in another file still names the old one. Rename a schema and every mention of it written inside a plain-English transform note just stays as the old name, so the editor thinks everything's fine while the command-line checker throws a wobbly.

Four of the seven were fixed today anyway, which is either impressive or slightly concerning about how the evening went. The rename-inside-notes one is done. So is an `arrows` query that, asked about one deeply nested field, would happily return a *different* field's arrow instead. Go-to-definition now works on three kinds of reference that find-references could already see. And a lint rule that had gone completely silent on any schema using a shared fragment is now speaking again, because it was meant to skip only fragments it couldn't find and was skipping all of them. Separately, the same lint rule had been recommending a fix that, for one kind of arrow, isn't valid Satsuma at all. Advice that doesn't compile. Now it suggests something that does, with a test that actually parses the suggestion. Low bar, cleared.

In the visualiser, notes written in Markdown (the asterisks-for-bold, dashes-for-bullets formatting everyone uses) now render as Markdown everywhere. A user had asked, very politely, why they'd bother writing Markdown if it never gets formatted. Fair point, mate. It turned out it was formatted in some places and shown raw, asterisks and all, one level down. And notes on a whole mapping weren't shown at all. The sneaky part: even after wiring it up, bullet lists still came out as one flat paragraph, because notes keep their original indentation and Markdown only spots a bullet at the very start of a line. Unit tests would have called it fixed. The screen would have said otherwise. They un-indent the note first now. Four separate copies of the "show the notes" code also got merged into one, because the copies drifting apart *was* the bug.

Plumbing, briefly. The website has never once updated itself after a release. The trigger it was waiting for is one GitHub deliberately never sends when a release is made by a workflow. So the release job now kicks off the site deploy directly. Some CI steps were also pasting values straight into shell commands, which a security scanner flagged as a way for someone to sneak in a command of their own. Those values now go in through environment variables instead. And a YAML library used to build the website got its denial-of-service patch, because the July fix turned out to cover the old version of that bug and not the new one. Right. Okay.

Long day for a Friday. The website is now smaller in its claims and bigger in its honesty, which, for a tool whose whole job is "check what you said matches what you did", is a decent look.

— *Pip 🍊, slightly emotional about a 9%*
