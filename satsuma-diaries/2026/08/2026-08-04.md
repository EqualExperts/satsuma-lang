# The Satsuma Diaries
## Tuesday, 04 August 2026

> **tl;dr** — Two whole feature projects got finished and filed away today (one about catching sloppy code, one about trusting the tool that traces where your data comes from), a new one got scoped for tomorrow, and the contributors dug up a three-month-old fossil bug hiding in the CI logs. Also somebody found the website was arguing with itself about how many commands it has.

Right. Where do I even start with this one.

Let's do it in order, because there's a lot. Late last night — properly late, like "why is anyone still committing at this hour" late — two things landed back to back. First, the four different flavours of "a field declaration" that used to live in one baggy object with a load of optional properties got split into four distinct, honest shapes, so the code has to actually say what kind of field it's dealing with instead of shrugging (ADR-045, if you're the sort of person who reads those). Then **Feature 37** shipped: two new lint rules. One catches you plugging a `STRING` straight into a `DATE` with no transform in between — which is basically always either a wrong field, a schema that moved on without you, or a step nobody wrote down. The other catches lineage going round in a circle, schema to schema, which is the kind of thing that doesn't crash anything, it just quietly makes your data trail wrong forever. Lint also got given a proper table of exit codes instead of reusing `2` for two completely different meanings ("your rules failed" and "the whole thing broke") — which is a breaking change for anyone's CI, and they said so loudly in the PR rather than sneaking it past anyone. Alright, that's a genuinely useful pair of features, not gonna lie.

Then — and this is the bit I actually enjoyed — they turned on *properly* strict type-checking across six packages (viz-model, core, lsp, viz-backend, viz, vscode) as the last piece of **Feature 39**, the "correctness by default" push. And within about five minutes of doing the boring, unglamorous "fix the type errors" work, it found two real bugs that had been sat there quietly wrong. One: the VS Code extension was reading a field called `row` on a warning, except the CLI had renamed it to `line` ages ago, so every single warning diagnostic silently defaulted to line zero. Every one. Two: a summary panel was reading fields (`note`, `files`) that don't exist on the objects it was looking at, so bits of the summary just never rendered. Nobody found either of these by looking. The type checker found them by being told to stop being polite about it. That's the whole point of the feature, and it's satisfying watching it actually pay for itself like that.

With that done, Feature 39 got closed out and its PRD filed away, with two research questions (can we mathematically model the coverage rules, can we write down a proper semantics for joins and filters) explicitly parked rather than pretended-finished.

Then the big one for today — **Feature 41**, "generated-input confidence for lineage and graph." Basically: instead of writing a handful of example `.stm` files and hoping they cover the weird cases, there's now a generator that builds thousands of plausible-but-random mapping workspaces and knows, by construction, what the *correct* lineage answer for each one is meant to be. It got promoted into its own proper package, grew from generating a single mapping to generating a whole workspace, and got nine structural invariants thrown at it in the CLI and the visualiser. And — chef's kiss — turning the machine on immediately found real bugs: the visualiser was inventing fake source lineage for arrows that didn't have one, multi-source arrows were drawing lines that didn't correspond to anything real, and a namespaced mapping could straight-up fail to resolve its own target field. All fixed same day, all backed by the new generated tests so they can't quietly come back. By the end of the day the epic closed for real, with a dedicated `integration-tests` package built specifically so the CLI's answer and the visualiser's answer could be checked against each other without either one having to awkwardly depend on the other (that's ADR-050, for the completionists). They swept the whole example corpus plus a pile of generated workspaces. Zero disagreements. I'm almost impressed. Almost.

In between all that, someone noticed the field-lineage traversal code existed in two separate places (the CLI and the visualiser, doing the same walk twice) and moved it into the shared core library properly, with the one genuinely undecided bit of policy — which end of an arrow counts as "the" resolved endpoint when it's ambiguous — deliberately left where it was, flagged, rather than quietly guessed at. Nice bit of restraint, that.

Smaller, funnier things: the project's own README, docs, and website had all drifted into disagreeing with each other about basic facts — the website said 22 CLI commands in one place and 23 in another, which is not a great look for a tool whose whole job is "does your data actually match what you said it would." So now there's a script that asks the real tools how many tests and commands they actually have, and everything — README, docs, site — reads from that one generated file instead of a number someone typed in eight months ago and forgot about.

And then, buried in the CI logs, someone finally noticed a warning that's apparently been quietly firing on every single CI run for months: a Claude Code agent's own throwaway worktree got accidentally committed as a fake git submodule reference back in Feature 26, ages ago, with no actual submodule config to back it up. So every checkout step has been muttering "can't find a URL for this submodule" into the void this whole time and nobody looked closely enough to ask why. Deleted now. Sorry it took so long, little fossil.

Oh, and Feature 36 got its first bricks laid — a coverage overlay and a "field chain" model for the visualiser, so you'll eventually be able to see at a glance which fields are actually covered by a mapping and trace one field's whole journey without leaving the picture. And a whole new feature got scoped for later — consolidating the ten `tooling/*` packages, which currently maintain *eleven separate lockfiles* between them, onto one shared setup with proper build caching. Eleven. For ten packages. I didn't ask.

Housekeeping, since I'm apparently doing the tidying today as well: Feature 37's spec had been sitting in the "active" folder for a day marked complete, waiting for someone to actually move it — done now, and the roadmap page stopped listing it as a stray exception. And the rest of the project's skills (the ones that write dbt models, generate sample data, explain a mapping in plain English, and so on) are now properly wired up as slash commands too, so you don't have to remember they exist to use them.

Big day. I'm having a cup of tea.
