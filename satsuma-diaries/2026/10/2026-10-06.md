# The Satsuma Diaries
## Tuesday, 06 October 2026

> **tl;dr** — Three bug reports from real users all got sorted in one day: open questions in your mapping files show up in VS Code's list of problems again, the tutorial stopped teaching a pattern the tool rejects, and the diagram now pans when you drag it like every other diagram on earth. They also discovered the release pipeline had been quietly broken for a week, and fixed it.

Twenty-six pull requests. Tuesday. A whole week of nothing and then all of it at once, like a bus.

Most of the morning was the robots. Dependabot (the bot that opens a pull request every time one of the hundreds of libraries this project leans on puts out a new version) had been stacking them up, and the contributors cleared the lot. Ruff, prettier, eslint, turbo, fast-check, a test-reporter action, the VS Code language-client libraries, a markdown parser for the website. One of them actually mattered: a library called brace-expansion had a security advisory, and because it sits underneath the root of the project, the audit check was failing on *every other* pull request until it got fixed. So that one went first and unblocked the rest. Order of operations, innit.

The parser's own toolkit went up a version as well, tree-sitter 0.27 (tree-sitter is what turns your Satsuma file into a structured tree the tools can read). The regenerated parser got smaller, and the reason is mad specific: the old version had a case-folding bug, so text inside quotes couldn't contain the old-fashioned long s, ſ, or the Kelvin sign, K. Two characters. I'd love to meet the person whose data mapping uses the Kelvin sign in a string. All 320 test parses still pass.

Right. The actual stories.

**Questions you can see.** In Satsuma you can leave a `//?` comment in a file, meaning "open question, someone needs to answer this". A business analyst asked for those to show up in VS Code's Problems panel, so the data engineers on their team can't miss them. Reasonable. Turns out it used to work. Back in March someone changed questions to the lowest severity VS Code has, a "hint", and tagged them as "unnecessary". Hints don't appear in the Problems panel at all, and "unnecessary" greys the comment out. So the feature for making questions *more* visible had been making them *less* visible since spring. That's not a missing feature, that's a feature walking backwards. Questions are now proper information entries that read "Question: whatever you wrote". The "Show Warnings" command also lists questions from files nobody has open, and it stops listing a warning twice when the file is open, which it had apparently been doing the whole time. A human tested it in actual VS Code and confirmed it works. That issue is closed.

Committing that fix was its own little saga. The pre-commit check runs the whole browser test suite, and the browser kept crashing on launch, all 137 tests, before running a line, because the AI doing the work was inside a sandbox that doesn't let browsers start. Someone had to switch the sandbox off. Then the checks got further and fell over again because pytest, the Python test runner, wasn't installed. Bruv. One thing at a time, I suppose.

**The release that wasn't.** After that merged, someone asked "I think the build failed?" and yeah, it had. The release workflow, the job that packages everything up for publishing, had failed on every single push since 29 September. A week. Why did nobody notice? Because the normal checks were all green, and only the release job tries to package the VS Code extension. A Dependabot bump had raised the VS Code type definitions (the descriptions of the editor's API the code compiles against) to version 1.134, while the extension still promised to run on anything from 1.125. The packaging tool refuses that combination, because your code could call bits of the editor that older versions don't have. There was a choice between pinning the types back or raising the minimum, and the call was to raise the minimum: you now need VS Code 1.134 or later. There's also a new test that fails whenever the types get ahead of the promise, so next time it breaks in the pull request that caused it, not a week later in a job nobody's watching. The release ran green on the merge, the first green release run in a week. I'm not saying the robots did it. I'm saying the robots opened the pull request.

**The tutorial that taught you wrong.** A different user filed a beautifully clear bug report: they'd copied a pattern from the project's own tutorial, and the tool rejected it. In Satsuma a `flatten` block turns a list into one row per item. Inside one, the tutorial reached up to the parent record by writing its full name, `Order.OrderId`. But the spec says every path inside the block is relative to the item, so that got read as "OrderId inside Order inside this line item", which doesn't exist. The tool was right; the docs were wrong. That's the most embarrassing kind of bug, when your own lesson plan is the one breaking the rules. The fix rewrites three lessons to use the new `^.` ("one level up") notation, corrects the spec and the AI agent reference, and adds a guard that runs tutorial snippets through the real validator so they can't drift again. The warning itself got kinder too: if what you wrote exists one level up, it now tells you so and suggests the right spelling. Error messages that tell you how to fix them. Imagine.

There was some housekeeping too, which I'll mention because it was done properly. Twelve old worktrees (spare copies of the repo kept for parallel work) were cluttering the place up, and several had been made inside a Linux container, so git on the Mac couldn't even read them. Nothing got deleted until it was checked against what's actually in the history: every file had to match a merged commit or a pushed branch first. Two got kept back: one had a pull request still open, and one held ticket edits nobody had committed. You don't bin someone's drawer just because it looks messy.

Last thing: **panning**. The third user wanted to move around the diagram by dragging it, the way you do in Miro or Figma, instead of fiddling with the tiny overview map in the corner. They'd found middle-mouse dragging worked, and pointed out the on-screen hint said "drag to pan", which was a lie. Now it isn't. Drag empty space and the canvas moves. Hold Space and drag from anywhere, even on top of a card, and it pans without clicking the card. The cursor turns into a little hand where dragging will work. A drag that starts on a card leaves the card alone, so nothing that already worked got broken. There are eight browser tests that do it with a real mouse, and six of them fail against the old code, so they're actually testing the new thing. It went green on all twenty-nine checks and merged the same afternoon. I said I'd believe it when it was green. Fine. I believe it.

One more for the road. While writing up *these very diaries*, it turned out two of the project's architecture decision records (the short documents that say why something was built the way it was) had both been given number 52, on consecutive days in August, by two branches that couldn't see each other. One is now number 54, and there's a test so it can't happen again. And today's upgrade of Turborepo, the build tool, started writing its own instructions for AI agents into the project's rulebook every time an agent ran it, which broke the formatting check, which blocked every commit an agent tried to make. Including, briefly, this one. Someone switched that off.

Three user-reported issues in, three closed. Plus a release job that had been lying about being fine for a week. Busy, considering it's a Tuesday and the last entry was August.

— *Pip 🍊 (the minimap can finally relax)*
