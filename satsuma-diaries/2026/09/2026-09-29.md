# The Satsuma Diaries
## Wednesday, 12 August 2026 — Tuesday, 29 September 2026

> **tl;dr** — Seven weeks of near-silence, then one Tuesday morning where everything that had been piling up got merged at once. The website stopped bragging about how few tokens Satsuma uses and started saying what it's actually for: being readable. Three bug reports from real users got properly investigated. And a robot quietly broke the release process, which nobody would notice for a week.

Hello? Anyone?

Seven weeks. I'm not gonna pretend I wasn't checking. I was checking. Every few days, refresh, nothing. A bump to some testing library on the 18th. Another on the 25th. Couple in early September. Something called `@humanfs/node` went from 0.16.7 to 0.16.8 and I'll be honest, I don't know what it is and I didn't ask. That's not a project, that's a houseplant.

Except, look closer, and it's not even that. None of those got *merged* in August. They were all sitting there as pull requests that Dependabot (the robot that opens a little PR every time one of your dependencies releases a new version, whether you asked or not) had been politely stacking up outside the door like parcels for a neighbour who's gone on holiday. The dates on them are the dates the robot wrote them. The date they actually went in is the 29th. All of them. Same morning.

So: Tuesday, 29 September. The contributors came back.

First thing through the door, just after seven in the morning, was the website rewrite. And I actually rate this one, because it's a project being honest with itself. For months the marketing copy had been leaning on two claims: that Satsuma specs use fewer tokens than the alternatives (tokens being the chunks AI models read text in, which you pay for), and that AI tools give better results when you hand them Satsuma. The first one is measurable but a bit of a nerdy flex for a homepage. The second one nobody had actually measured. So both went. The homepage now leads with the thing that's genuinely true and genuinely the point: it's a readable language for describing how data moves from one place to another, that people and AI tools can both use. "Measurably Leaner" became "Version-Controlled". "AI-Native" became "Works with AI Tools". "The superpower" became "Extensible metadata", which is less fun but more accurate, and I respect a demotion. The FAQ question about whether non-technical people can read it got moved to the top, which is where it should have been all along. The bit I liked most: the PR description says it doesn't *argue* against the old claims, it just stops making them. No grovelling, no "we were wrong" page. Just quietly stop saying things you can't back up. More of the internet should try it.

Funny detail though. The PR admits it wasn't checked visually. Whoever was driving tried to screenshot the pages and the headless browsers (the invisible ones that run without a screen, for automated testing) just crashed on launch. Both of them. Chrome *and* Firefox. Couldn't even get a picture. So a PR whose whole job was making the website look and read better went in with a note saying "please could a human look at this on their phone." Love that for us.

Then the parcels. Fourteen Dependabot PRs merged in one sitting, oldest to newest. esbuild, eslint, turbo, a Python linter, a GitHub Action that deploys the website, all the usual. Most of it is the software equivalent of changing the batteries in the smoke alarm. But one of them, and I'm putting a pin in this, was `@types/vscode` going from version 1.125 to 1.134. That's the file that tells the code what the VS Code editor's toolkit looks like. Sounds harmless. Hold that thought.

Also merged that morning, after sitting there since the 11th: the escape hatch for nested data. I'm not doing it twice, because the entry for the 11th covers it, but the short version is that inside a "for each item in this list" block you can now say `^.` to mean "go up one level" or `$.` to mean "start from the top", instead of the language assuming everything you write is about the current item. Seven weeks it waited. It's in now.

Then the bit that actually made the day feel like a day. Three issues, filed back in August by real people using the thing, finally got sat down with properly. Not just labelled and left. Investigated.

The first one was from a business analyst who wanted the `//?` comments to show up in VS Code's Problems panel. (`//?` is how you write "open question" in a Satsuma file, like a sticky note saying "someone needs to check this.") They'd filed it as a feature request. Turns out it was a *regression*, meaning it used to work and someone broke it. The original design said questions should appear as "information" in the panel, and at some point back in March they'd been quietly downgraded to "hints", which VS Code doesn't list at all, and on top of that tagged as "unnecessary", which makes the editor grey them out. So the exact thing a BA uses to say "this needs attention" was being displayed as "ignore this." You can't make that up.

The second one was the good one. Someone wrote a mapping exactly the way the tutorial told them to, and got an error. Copied it from our own docs. Got told off by our own tool. And the investigation found the tool was *right*: the spec says every path inside one of those "for each" blocks is relative to the current item, so `Order.OrderId` inside a loop over order lines means "the OrderId field of an Order field inside this line item", which doesn't exist. The tutorial, two lessons, and a bit of the spec itself had all been teaching the wrong pattern. So two tickets: fix the teaching material and add a check so doc examples can't drift from what the validator accepts again, and make the error message stop sounding like a bug and start suggesting the `^.` fix. The reply on the issue actually thanks the person and admits "that's our mistake", which, again, nice.

The third one was a request for proper canvas panning in the visualiser, Miro-style, click-and-drag on empty space. The reporter had already found that middle-click dragging works, and pointed out the little hint on screen literally says "drag to pan", which is just not true if you use a normal left click. So that's two tickets: correct the lie on the screen, and build the thing they actually asked for.

Five tickets filed that morning, each one with a root cause written out, which file and which line, and what "done" looks like. On a Tuesday before nine. Fine. I'm not saying anything.

And now the pin. That `@types/vscode` bump from earlier? The VS Code extension promises it works on editor version 1.125 and up. The new type file describes version 1.134. And the tool that packages the extension into an installable file looks at that and goes: hang on, you're describing features from 1.134 but promising to run on 1.125, I'm not building this. Refuses. Flat out. So from twenty past seven that morning, every single run of the release workflow failed.

Nobody noticed. Because the normal checks, the ones that go green or red on every PR, never actually package the extension. Only the release job does. So everything looked fine. Green ticks everywhere. Meanwhile the one job that makes a downloadable thing was face-down on the floor. It stayed like that for a week.

I'll tell you how that ends next time. Spoiler: someone notices.

Seven weeks of nothing and then a morning of honesty, bug archaeology and an unexploded robot. Classic.
